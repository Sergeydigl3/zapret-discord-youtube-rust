# Руководство по участию (Contributing Guidelines)

Добро пожаловать в разработку `zapret-rust`! Мы рады любым пулл-реквестам, идеям и исправлениям. 

Чтобы автоматизировать процесс создания релизов и подготовки Changelog, мы используем строгие правила интеграции изменений в основную ветку.

---

## 🗂 Куда класть новый код

Проект разбит на три пакета, и границы между ними проверяет компилятор:

- `src/` — только бинарник: bootstrap, разбор аргументов, цикл приложения.
- `crates/zapret-core` — доменная логика. Зависимости внутри пакета идут **только вниз**, по таблице слоёв.
- `crates/zapret-tui` — интерфейс. Зависит только от `zapret-core` и ничего не экспортирует обратно.

Перед тем как создать модуль, загляните в `docs/architecture.md`: там таблица слоёв и правило «одна ответственность — один модуль». Если новому модулю нужно что-то из слоя выше, граница неверна — выносите общее вниз. Если два модуля делают одно и то же, скорее всего, это уже есть в `paths` или `process`.

Для TUI: экран — это вариант в `state/screens.rs`, обработчик в `state/actions/`, отрисовка в `draw.rs` и модуль в `menus/`. Логика экрана не должна попадать в `session.rs`, а рендер не должен содержать логики.

## 📌 Основные правила (Release Please & Conventional Commits)

В проекте настроен автоматический выпуск релизов с помощью инструмента **Release Please**. Робот читает коммиты в ветке `master` и на их основе автоматически:
1. Вычисляет новую версию (по правилам SemVer).
2. Обновляет версию в `Cargo.toml`.
3. Генерирует красивый `CHANGELOG.md`.
4. Создает GitHub Release и прикрепляет к нему бинарники.

> Версию робот bumps **только** в корневом `Cargo.toml`. У пакетов в `crates/` (`zapret-core`, `zapret-tui`) проставлена та же версия, но она не обновляется автоматически: эти пакеты не публикуются, и падение цифр на них ни на что не влияет. При желании синхронизируйте их вручную в том же коммите, что и релиз.

Чтобы робот всё правильно понял, **названия коммитов в `master` должны строго следовать стандарту [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/)**.

## 📝 Требования к Pull Request'ам

При принятии PR мы чаще всего используем **Rebase and merge**. Это означает, что **каждый ваш коммит** из ветки попадёт в итоговую историю `master` как отдельная запись.

Поэтому **КРАЙНЕ ВАЖНО**, чтобы **и заголовок PR, и каждый отдельный коммит** в вашей ветке были названы строго по стандарту Conventional Commits. Именно из этих коммитов `Release Please` будет собирать финальный `CHANGELOG.md`. Если коммиты названы неправильно, они могут не попасть в историю релиза.

### Формат заголовка:
`тип(опциональный скоуп): краткое описание на английском`

**Допустимые типы:**
- **`feat`** 🚀 — Новая функция (автоматически увеличит MINOR версию, `0.1.0` → `0.2.0`).
- **`fix`** 🐛 — Исправление ошибки (автоматически увеличит PATCH версию, `0.1.0` → `0.1.1`).
- **`perf`** ⚡ — Улучшения производительности.
- **`refactor`** ♻️ — Рефакторинг кода (без изменения поведения программы).
- **`docs`** 📝 — Правки только в документации (`README.md`, комментарии).
- **`chore`** 🔧 — Обслуживание, правки CI, обновление зависимостей (`Cargo.lock`).
- **`style`** 🎨 — Форматирование кода (прогонка `cargo fmt`, удаление пробелов).
- **`test`** ✅ — Добавление или исправление тестов.
- **`ci`** 👷 — Настройка CI/CD (GitHub Actions, деплой и т.д.).

*(Типы `style`, `test` и `ci` скрыты от пользователей и не попадут в итоговый CHANGELOG).*

### ✅ Примеры хороших заголовков PR:
- `feat: add autotune presets support`
- `fix: resolve crash on socket close`
- `docs: update Windows build instructions`
- `chore: bump clap dependency to 4.5`

### ❌ Примеры плохих заголовков PR (CI не пропустит):
- `Fixed crashing` *(нет типа `fix:`)*
- `Added tests` *(нет типа `test:`)*
- `Update README.md` *(нужно `docs: update README.md`)*

## 🛠 Порядок работы

1. Сделайте форк (Fork) репозитория.
2. Создайте ветку для ваших изменений: `git checkout -b feature/my-feature`.
3. Внесите изменения в код, убедитесь что `cargo clippy` и `cargo test` проходят успешно.
4. Запушьте ветку: `git push origin feature/my-feature`.
5. Откройте Pull Request в основной репозиторий.
6. **Внимательно назовите PR**, добавив префикс (например, `feat: ...`).
7. Дождитесь успешного прохождения проверки **Lint PR Title** и тестов.
8. Мейнтейнер проверит ваш код и сделает **Rebase and merge**!

Спасибо за ваш вклад! ❤️
